# Prepared Metrics and Typed Ranking Read Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Przyspieszyć Ranking i Rider Details z preagregacją, zachowując identyczne wyniki i publiczne odpowiedzi.

**Architecture:** Przygotowane składowe sesji powstają obecnym kalkulatorem C# i są zapisywane warunkowo względem rewizji źródła. Typowany odczyt rankingu rozdziela rekordy wyników od metadanych i współdzieli przygotowanie sesji w obrębie żądania. Dotychczasowy odczyt pozostaje fallbackiem i wzorcem zgodności.

**Tech Stack:** ASP.NET Core net10.0, System.Text.Json, xUnit, PostgreSQL/Supabase, istniejący klient REST; bez nowych zależności aplikacji.

**Spec:** `docs/superpowers/specs/2026-10-03-preaggregation-read-path-design.md`

## Global Constraints

- Nie zmieniać wyników obliczeń, kategorii, filtrów, sortowania, porównania pozycji, publicznych DTO ani wyglądu.
- Nie wydłużać czasu ważności ogólnego cache API. Frontend pozostaje bez zmian.
- Punktem odniesienia jest bieżący kod lokalny, nie starszy commit.
- Oryginalne czasy wyników i sektorów pozostają niezmienione.
- Nie duplikować kalkulatorów dla nowej reprezentacji.
- Zapisy tylko rolą serwisową; zachować zasady publicznego odczytu.
- Nie publikować przy okazji innych lokalnych zmian. Commitować wyłącznie zweryfikowane, wskazane pliki.

## Review Focus

- Zmiana źródła podczas przygotowania: stary zapis nie może nadpisać nowej rewizji (zadanie 2).
- Filtrowanie statusów i kategorii: preagregacja innej populacji nie może zmienić ocen (zadanie 4).
- Historyczne nazwy i teamy: zachować globalne last-row-wins oraz pierwszeństwo historii (zadanie 5).
- Niepełne splity, DNF/DNS/DSQ i brak klasyfikacji: nie fabrykować korekty czasu (zadanie 3).
- Anulowanie/błąd współdzielonego przygotowania: kolejna próba musi działać; bez mutacji drugiego rankingu (zadanie 5).

## Organizacja pracy

Ścieżki poniżej są względem repozytorium `UCI_Stats_API`; kod aplikacji jest w podkatalogu o tej samej nazwie. Przed wykonaniem zastosować using-git-worktrees. Izolacja musi zawierać bieżący brudny stan jako bazę; nie zgubić wcześniejszych poprawek ani nie włączyć plików tymczasowych. Referencyjny serwer użytkownika pozostaje uruchomiony.

Każde zadanie implementacyjne: test RED, minimalna implementacja, test GREEN, przegląd diff, lokalny commit tylko jego plików. Brak nowych publicznych endpointów. Przełączniki diagnostyczne dwóch nowych ścieżek domyślnie wyłączone do zakończenia zgodności.
