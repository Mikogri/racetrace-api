# Dane, pakiety wejściowe i cache

PostgreSQL przechowuje fakty zawodów: rundy, sesje, zawodników, wyniki, pomiary, przyznane punkty i historię zespołów. API pobiera je przez Supabase/PostgREST oraz RPC. Baza ogranicza koszt powtarzanych złączeń i transportu, ale bieżące kalkulatory sportowe nadal wykonują się w C#.

## Import i dane źródłowe

`20261030171154_cache_invalidation_safeupdate.sql` fixes global package invalidation in `racetrace_private.calculation_source_changed`: the intended full deletion uses `WHERE session_id IS NOT NULL` (a non-null key), keeping pg_safeupdate enabled. The previous unqualified DELETE caused HTTP 400 during competition-rank updates and blocked planned-round imports. Applied to RaceTrace and verified with an update inside a rolled-back transaction: invalidation ran, then all 492 packages and the revision digest were restored. No source results, calculator formulas or import records were changed by that test.

Kontrolery administracyjne przyjmują import sesji, formularz rundy i PDF. Fetchery ChronoRace/Tissot pobierają format dostawcy, mappery sprowadzają go do wewnętrznego modelu, a warstwa zapisu wykonuje upserty partiami. Uzupełnianie wyników i ponowny import pozostają osobnymi operacjami. Danych z bieżącego Live nie należy utożsamiać z zapisanymi wynikami historycznymi.

Importer ChronoRace przyjmuje wyłącznie HTTPS na `prod.chronorace.be`, `www.chronorace.be` lub `chronorace.be`, bez danych logowania i portu innego niż 443. Tissot zachowuje własną listę oficjalnych hostów i również odrzuca takie porty oraz dane logowania. Klienci HTTP tych importerów i proxy ChronoRace nie podążają automatycznie za przekierowaniami. Nowy adres dostawcy wymaga świadomego dopuszczenia w kodzie, a nie wyłączenia kontroli dla dowolnego URL.

Odpowiedzi JSON tych trzech klientów mają limit 16 MiB sprawdzany również podczas odbioru bez `Content-Length`. Odczyt body ma budżet 30 s; klient HTTP ma osobny timeout żądania 30 s. Przekroczenie rozmiaru daje `UPSTREAM_RESPONSE_TOO_LARGE`, nie częściowy import. Te zabezpieczenia nie są pełnym audytem wszystkich integracji: obrazy, PDF, przeglądarka Pinkbike, ograniczenia sieci wychodzącej i konfiguracja hostingu wymagają osobnej kontroli przed publikacją.

Splity są czasami narastającymi; sektory powstają z różnic kolejnych wiarygodnych pomiarów i mety. Brak lub nieprawidłowy checkpoint nie może tworzyć fikcyjnie szybkiego sektora. Cztery pośrednie splity i meta dają pięć sektorów, ale brak dowodu pozostaje brakiem. Korekta incydentu w kalkulatorze nie nadpisuje oficjalnego przejazdu.

Team przy wyniku ma pierwszeństwo. Przy jego braku używane jest przypisanie z `rider_team_history` obowiązujące w dniu sesji. Historia zapisuje okres, źródłową rundę i co najwyżej jeden otwarty okres ridera. Import bez teamu nie powinien zamykać historii. Ranking dobiera team do ostatniego wyniku w wybranym zakresie, nie zawsze do obecnego zespołu.

Punkty są przyznawane według reguł systemu punktowego i przechowywane oddzielnie od Ratingu/ResultScore. Zmiana tabeli punktów może wymagać administracyjnego przeliczenia przyznanych punktów; samo przeładowanie kalkulatora Pace tego nie wykonuje.

Obrazy rund mają osobną ścieżkę odczytu, zamiast base64 w ciężkich odpowiedziach. `RoundImagePayloadParser` konwertuje obraz do WebP z jakością 88; import i administracyjna konwersja korzystają z tej interpretacji. Operacja konwersji istniejących plików jest jawnym zapisem, nie zadaniem startowym API.

## Round list transport

The standard season round list uses one PostgREST request, embedding session statuses through `round_categories` and image paths through `round_images` / `tracks.venue_images`. It does not fetch image binaries. Existing reference/status filters can still require preparatory reads; the one-request guarantee applies to the standard season listing. Public DTO fields, pagination and status rules are unchanged. Storage-backed images return direct public URLs; legacy binary images retain the API endpoint fallback. Results cards use `imageUrl` rather than rebuilding that endpoint. Results and Live card entrance durations are 100 ms; Results stagger is 100 ms.

`dotnet run --project tools/ReadPathParity -c Release -- --round-list-benchmark` compares the former three sequential reads to the new list service against the same database. Five local samples on 2026 returned 10 rounds / 10 direct Storage URLs; median old read time was 273 ms versus 91 ms for the new service. This is not a deployed browser latency measurement. The probe checks total counts; unit tests enforce one standard read, binary exclusion and legacy/Storage image behavior.

## Odczyt rankingu i profilu

Najpierw wybierane są sesje pasujące do filtrów. Dlatego w logach Supabase mogą występować żądania `/sessions`, mimo że przeglądarka wywołała `/api/v1/ranking`. Dopiero kolejnym krokiem jest pobranie pakietów wejściowych albo danych surowych. Nie istnieje obowiązek zgodności ścieżki własnego endpointu z tabelą odczytywaną przez PostgREST.

`get_ranking_input_packages` zwraca zwarte dane sesji; `get_rider_input_data` zwraca zawodnika i pole potrzebne do porównań. Format `v:3` zawiera sesje `s`, wyniki `r`, metadane riderów `d`, teamy `t`, referencje pola `f` w detalach, źródłowe pomiary narastające `ix` i opcjonalne dane prezentacji splitów `x`. `p_include_splits=false` pozwala rankingowi nie przesyłać niepotrzebnych danych wyświetlania.

Pakiety nie zawierają końcowych Pace, Consistency i Ratingu. API odtwarza sektory, rozkłady pola, oznaczenia incydentów, korekty i metryki dynamicznie. Opcjonalne `ia` w bazie zawiera eksperymentalne oznaczenia istniejącego detektora dla całej sesji, nie wynik modelu ML. Bieżący parser ignoruje `ia`: benchmark nie uzasadnił aktywowania tego cache. Istotne jest pełne pole odniesienia przed filtrowaniem pojedynczego ridera; wyszukiwanie nie może zmieniać sportowego znaczenia jego tempa.

`IncidentAnnotationCache` zapisuje identyfikatory i krótkie znaczniki normalnych sektorów; anomalie zachowują pełne diagnostyki. Kontener binarny jest kompresowany Brotli i przesyłany jako Base64. Diagnostyki normalnych sektorów są odtwarzane tym samym kodem matematycznym co detektor. Niepoprawny zapis, inna wersja lub niestandardowa konfiguracja Pace powodują powrót do liczenia dynamicznego. Nie zmienia to oficjalnych czasów ani potwierdzonych etykiet badawczych.

Migracja `20261027132839_stored_sector_incidents.sql` dodaje trzy kolumny techniczne i RPC `save_ranking_incident_annotations`, dostępne wyłącznie dla `service_role`. Zapis porównuje `source_revision`, więc wynik przygotowany przed zmianą źródła nie nadpisuje nowszych danych. Zmiana `payload` lub `input_splits` unieważnia oznaczenia. Zwykły import nie odbudowuje oznaczeń; administracyjny tryb `incidents` i narzędzie `--prepare-incidents` pozostają jawnymi operacjami eksperymentalnymi. Nie włączają ich odczytu w aplikacji.

`RankingInputPackageReader` sprawdza kompletność zestawu sesji. Brak pakietów nie może skutkować częściowym rankingiem udającym kompletny. Ścieżki surowe i starsze kontrakty RPC pozostają fallbackiem; błąd autoryzacji lub sieci nie powinien być ukrywany jako zwykły brak pakietu. Detale potrafią użyć surowego źródła także dla nieobsługiwanego przez reuse filtra statusu.

`ReadOptimizations:TypedRanking=true` włącza typowany odczyt. Historycznie nazwana flaga `PreparedRiderDetails=true` oznacza dziś ponowne użycie **pakietów źródłowych**, nie zapisanych wyników kalkulatora. Obie są włączone w repozytoryjnym `appsettings.json`.

## Co wymaga przebudowy

Zmiana wzoru lub wagi kalkulatora wymaga wdrożenia nowego API oraz odświeżenia obliczonych odpowiedzi, nie przebudowy źródłowych pakietów. Zmiana detektora lub jego progów zmienia wersję oznaczeń incydentów: niezgodne oznaczenia są ignorowane do ich odbudowania. Samo strojenie wag niezależnych od detektora nie zmienia tej wersji. Zmiana wyników, pomiarów, przyznanych punktów albo schematu wejścia wymaga odświeżenia źródła i pakietów. `input_splits` zachowuje także brakujące i nieprawidłowe obserwacje potrzebne interpretacji danych.

### Verification: stored annotations (2026-10-27)

The production database migration and backfill covered 492 sessions (369,824 encoded characters). Source revisions remained unchanged. Local Release tests: 906 passed; complete serialized Pace outputs matched for 21,371 runs. Stale-revision writes were rejected and source-update invalidation was verified in a rolled-back transaction. No research ML model was activated.

Five fresh-service samples per case used the real Supabase read path, including decoding and calculation, but not browser/proxy delivery. Median milliseconds without/with annotations: ranking 2026 **1063.7 / 1058.7**, all-season ranking **2055.0 / 2207.3**, rider 2026 **785.3 / 806.4**, all-season rider **1638.5 / 1599.9**. All response bytes matched. This is not evidence of a general latency improvement: transfer grew by about 5–9%, and all-season ranking regressed 7.4%. Network timings merge concurrent waits and do not isolate database execution. An earlier full-JSON annotation format regressed further and was replaced with sparse encoding.

The measured experiment temporarily connected `IncidentAnnotationCache.ReadPackages` to the compact parser; that connection was removed before publication. `tools/ReadPathParity --incident-cache-benchmark --phase before|after --output <directory>` measures the current read path, not an automatic cache-mode switch. `--prepare-incidents` performs an authenticated derived-data backfill and must target the intended database. Local historical artifacts are under `artifacts/stored-incidents-compact/`. The migration and backfill were applied to the database; the released runtime remains dynamic and does not rebuild or consume stored annotations.

Normalne odświeżanie używa `refresh_ranking_session_preaggregate`; tryb `missing` sprawdza dostępność wejść. Dawne kolumny `prepared_payload` i `prepared_version`, RPC przygotowanych metryk oraz `RankingPreaggregationService.PrepareAsync` zachowano dla kompatybilności i jawnych narzędzi powrotu. Bieżąca ścieżka ich nie konsumuje, a zwykły import nie przygotowuje kalkulatorozależnych wyników. Samo istnienie tych nazw nie oznacza, że należy je odbudowywać po każdej zmianie wzoru.

## Warstwy cache

Ranking v3 source preparation decodes the combined result field once and prepares missing session inputs in a batch, retaining per-package scoped reuse for previous-round comparisons. It does not change calculators or cache lifetimes. `ReadPathParity --parser-benchmark` isolates CPU/allocation costs using real Supabase packages and checks all rider metrics for exact equality. On the full Elite Men history, warm preparation remained roughly 0.42 s, while allocations fell from about 468 MB to 418 MB (~11%). The five-sample full-request comparison in `artifacts/ranking-materialization/` preserved all response fields; ranking 2026 medians were 1119/1031 ms, all-season 1972/2025 ms. These noisy figures do not establish an overall latency improvement.

## Bundled reads and verification (2026-10-29)

Context filters use one `/api/v1/filter-options` request and `get_filter_options` RPC, retaining five-minute freshness. Results still loads seasons only. SQL respects table RLS and existing dictionary limits/order; direct read-only validation returned 6 seasons, 17 tracks, 6 conditions and 2 classes (1,769 UTF8 bytes of JSONB text). The new RPC migration must precede API/frontend deployment.

Home's Top Rated and Standings use `/api/v1/home/ranking`, sharing a frontend query per season/category and the existing ranking snapshot. Different category controls remain independent. Both full ranking payloads match their former separate requests. This removes one HTTP request when selections match, not another database calculation: the existing snapshot was already shared. Sequential local medians varied from 834 ms before to 1,107 ms after with different network waits; do not claim a proven latency improvement from this noisy comparison. The Home endpoint uses the heavy-request concurrency limiter.

Compare lazily requests `get_compare_input_data` once on cache misses, retaining full session fields and projecting each rider's results/splits/points separately. Snapshot identity, revisions, provenance and per-rider formulas remain unchanged. Only a missing RPC (`PGRST202`/404) falls back to scalar reads; authentication, malformed data and other failures propagate. A missing migration adds a failed lookup, so apply migrations before deployment. Read-only SQL plus local injected-package verification produced byte-identical API responses for riders 18/183 (2026 and all years), and asymmetric riders 18/8 (2026). Cold reads were 4 versus 3, warm additional reads zero; shared database JSONB-text bytes fell 20.48% / 5.51%. This was not a deployed new-RPC latency test. Proofs: `artifacts/feature-bundles/compare-{sql,api-injection}-proof.json`.

### Profiling and production boundaries

Bounded operation names now identify `input_decode`, `field_prepare`, `incident_detection`, `pace`, `consistency`, `rating`, `ranking_projection`, `ranking_total` and rider history. Operations nest: never sum them as independent wall-clock phases. In one representative all-season sample, total time was 2,193 ms, overlapping Supabase waits 1,032 ms, other application time 1,161 ms; input decode 211 ms, field preparation 406 ms (including incident work), incident detection 231 ms and rating 342 ms (including child calculations). No exact SQL execution duration is inferred from HTTP waits.

Use `tools/ReadPathParity` with `--incident-cache-benchmark --phase before|after --output <folder>` for unchanged-response comparisons; add `--features` for Compare/Home, `--home-only` to isolate Home, or `--warm` for a shared memory cache. Five samples include first-use JIT/connection costs. Warm ranking samples were roughly 4–17 ms and zero Supabase calls; this does not describe a cold production request. `--production-http` records actual deployed Cloudflare and direct-API GET timings; local credentials currently receive 401 directly, so direct application latency remains unverified. Secrets are not recorded. No cache purge, restart or production deployment is performed.

The frontend script `scripts/benchmark-production.mjs` accepts an existing `PLAYWRIGHT_MODULE` and records real navigation, paint and resource timings in a fresh browser context with a bounded observation window. Production samples showed 13 API responses for Results (including ten image redirects), six each for Ranking, Compare and Home. Browser API duration varied markedly from simple HTTP samples (e.g. ranking ~6.6 s versus ~0.2 s for warmed HTTP); these are different cache/connection samples, not an attributed browser CPU regression. FCP is not time-to-loaded-data. Cloudflare's new `Server-Timing: upstream_headers` measures gateway-to-upstream headers only, preserves API timing and streams the body unchanged; it becomes available only after frontend-function deployment. It is not SQL duration or full body transfer.

After explicit operator approval, the additive RPC migrations were applied to RaceTrace Analytics on 2026-10-29 as `20261029195017_filter_options` and `20261029195018_compare_shared_rider_input`. API/frontend code was not deployed or published. The existing `get_rider_input_data` definition hash remained `fc31ef041b2789ebb66b6283553caed8`; 21,462 results, 79,562 splits and the package source-revision digest were unchanged. Both new functions run as invoker with an empty search path; the security advisor reported no new findings (existing unrelated warnings remain).

Real HTTP RPC validation after migration: bundled filter dictionaries matched all old values/order, four concurrent requests became one, with five-sample medians about 91/84 ms and a 1,604-byte serialized DTO. Full Compare response bytes matched the scalar baseline: 2026 median 685/644 ms, all seasons 1,355/1,355 ms; calls 4/3 and downloaded decoded HTTP bytes 342,770/272,687 (2026), 1,666,488/1,574,722 (all). These modest/no latency changes must not be presented as a proportional speedup. Home response parity also passed. Reproduce with `--filter-benchmark`, `--features`, and `--features --asymmetric-only`; outputs live under `artifacts/feature-bundles/`. No final calculator outputs are stored by these changes.

The separate real-RPC asymmetric 2026 comparison (riders 18/8) also preserved exact response bytes and reduced decoded transport from 301,260 to 249,789 bytes and calls from 4 to 3, but sequential median latency increased from 539 to 637 ms. This is a measured tradeoff, not a universal latency win; repeat paired measurements before setting a production performance target. All these timings include local API work and real Supabase transport, not the deployed API/frontend pipeline.

Within a request, identical public category-ID lookups share one pending task in `DomainMetadataQueries`; service-role imports bypass that reuse. Rider overview starts its snapshot, points position and team history reads concurrently and passes the same history task to profile presentation. No cache lifetime, metric formula, public contract or filter rule changes. `ReadPathParity --incident-cache-benchmark --phase before|after --output <folder>` verifies complete response parity for ranking and rider overview against real Supabase reads, recording request count, transfer and stage timings. These changes are not a claim that Home, Compare or every filter has been consolidated into one database request.

Pakiety w pamięci procesu żyją 30 s i rozróżniają zakres danych, rolę oraz sesję. Parsowanie/przygotowanie tej samej niemutowanej paczki jest dodatkowo współdzielone wewnątrz jednego żądania. To inne mechanizmy niż trwała preagregacja w PostgreSQL.

`RankingService` przechowuje snapshot obliczeń przez 30 s. `RankingSingleFlight` scala nakładające się żądania o tej samej tożsamości w danym procesie; nie koordynuje wielu hostów. Sortowanie i paginacja korzystają z przygotowanych wierszy. Porównanie z ostatnią rundą lub wcześniejszymi filtrami może wymagać drugiego kontekstu obliczeń, ale nie musi ponownie przygotowywać identycznych sesji.

Output Cache przechowuje odpowiedzi endpointów objętych polityką: ranking 30 s, season overview i podium 60 s, analytics 5 min. Uwzględnia wszystkie parametry query; nie zapisuje błędów ani odpowiedzi z `Set-Cookie`. Autoryzacja pozostaje przed cache. `refresh=1` omija lookup i zapis odpowiedzi rankingu oraz wymusza jego przeliczenie, ale nie jest poleceniem usunięcia wszystkich cache aplikacji i bazy.

TanStack Query ma domyślnie 30 s świeżości i 5 min przechowywania nieaktywnych danych. Słowniki filtrów mają 5 min świeżości, wspólny klucz sezonów i odświeżanie przy wejściu, powrocie do okna lub odzyskaniu połączenia, jeżeli dane są nieświeże. Otwarcie dropdownu nie oznacza osobnego pobrania. `/api/v1/metadata` dostarcza etykiety, skróty i kolejność typów. Kategorie są utrzymywane przez katalog lokalny uzupełniany metadanymi i odpowiedziami API; nie mają oddzielnego endpointu kategorii. Nowy import nie jest natychmiastowym powiadomieniem przeglądarki. Live ma własny polling, opisany w [ARCHITECTURE.md](ARCHITECTURE.md).

## Rewizje i invalidacja

`CacheCoherence:Enabled` jest domyślnie wyłączone; nie jest jawnie włączone w śledzonym `appsettings.json`. Włączenie wymaga migracji `20261010210121_calculation_revisions.sql` i serwerowych uprawnień do RPC. `DataRevisionService` pobiera rewizje przez `get_calculation_revisions` najwyżej raz na 5 s aktywnej instancji, chyba że żądany jest wymuszony odczyt. Nie jest to timer automatycznie odświeżający UI.

Przy aktywnej spójności klucze cache uwzględniają zakres rewizji i fingerprint algorytmu. Output Cache sprawdza rewizję ponownie przed publikacją i nie zachowuje odpowiedzi powstałej w trakcie zmiany danych. Nieudane sprawdzenie rewizji nie przedłuża ważności starej; API może zwrócić błąd dostępności, zamiast potwierdzać niezweryfikowaną aktualność.

Triggery rewizji są atomowe w granicach transakcji PostgreSQL. Import składający się z wielu żądań REST nie jest jedną transakcją: jego części mogą być widoczne po kolejnych commitach. Rewizje pomagają odrzucić obliczenie obejmujące różne zaobserwowane stany, lecz nie zmieniają importera w atomowy batch. Przy wyłączonej spójności obowiązują starsze reguły TTL; nie należy obiecywać identycznej gwarancji invalidacji.
